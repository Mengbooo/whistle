# Whistle 工作机制说明

## 项目本质

Whistle 不是一个单纯的 RSS 阅读器，也不是一个只会抓取链接的聚合页。它的核心工作是把分散的信息源变成一份经过筛选、重排和重写的日报。整个系统重点不在“抓得多”，而在“先做一轮加工，再把结果用适合阅读和分发的形式输出出来”。

## 整体运行链路

Whistle 的主链路可以概括为：

`信息源配置 -> RSS 抓取 -> 文本清洗 -> 去重与过滤 -> 打分排序 -> 板块归类 -> Agent 重写成稿 -> HTML/PDF 产出 -> 网站归档与邮件分发`

这条链路里，前半段负责把原始信息处理成可用素材，后半段负责把素材变成真正可读的日报。

## 1. 信息源是怎么组织的

项目通过 `sources.yaml` 管理输入源。这里不仅定义了 RSS 地址，也定义了每个来源的权重、标签、默认板块，以及整份日报的结构规则。

除了 source 列表，`sources.yaml` 还控制几类核心参数：

- `profile`
  - 定义时区、语言、最多保留多少条、速报保留多少条、回看多少天内的信息。
- `sections`
  - 定义日报有哪些板块，每个板块最多几条、最少几条、关键词是什么、优先级多高。
- `topics.include / exclude`
  - 定义哪些关键词更值得保留，哪些关键词应优先排除。
- `relevance`
  - 定义哪些词属于“工作信号”，哪些词属于“噪音信号”。
- `ranking`
  - 定义时间新鲜度、来源权重、关键词匹配、重复惩罚等打分因子的权重。

这意味着 Whistle 的定制化不是写死在代码里，而是大量前置到了配置层。想让它偏 AI、偏开发、偏产品、偏投融资，本质上先改的是配置，不一定先改程序。

## 2. 抓取后做了什么预处理

系统启动后，会先读取 `sources.yaml`，筛出启用的 RSS 源，再逐个抓取 feed。抓回来的内容不会原样进入日报，而是先做一轮标准化处理，包括：

- 统一标题、链接、发布时间、摘要字段
- 去掉 HTML 标签、脚本和样式碎片
- 压缩摘要长度，避免单条素材过长
- 为每条内容补上来源信息、来源权重、来源标签和候选板块

这一步的目标是把不同来源的内容拉成统一结构，方便后续统一打分和过滤。

## 3. 去重、过滤和排序是怎么做的

这是 Whistle 最核心的一层。项目不是简单按时间倒序出结果，而是会对每条内容做一轮相关性判断。

系统会综合这些因素计算得分：

- 新鲜度：内容离当前时间越近，分数越高
- 来源权重：更重要的信息源可以给更高基础分
- 关键词命中：命中关注主题的内容会加分
- 工作信号：涉及产品、研发、增长、合规、商业化、基础设施等词的内容会加分
- 噪音信号：八卦、泛娱乐、传闻、弱相关消费电子等会扣分
- 重复惩罚：同源内容过多会被递减处理
- 板块匹配：如果内容与某个板块关键词高度匹配，会获得额外加成

去重也不是只看 URL。系统一方面会去掉同链接内容，另一方面会把标题做归一化，再用相似度比较识别“不同站点在转同一件事”的重复条目。

最后得到的是一份排序后的候选池，而不是直接发布结果。

## 4. 日报板块是怎么生成的

排序结束后，系统会按 `sections` 里的规则把内容分配到不同板块，例如：

- 今日头条
- AI 与新工具
- 大厂与平台动态
- 产品与增长观察
- 开发者与工程实践
- 投融资与行业机会
- 政策监管与合规
- 社交热度观察

每个板块都有自己的容量限制和关键词范围，因此不是“分数最高的内容全部堆在一起”，而是先保证结构完整，再在结构内挑最值得保留的条目。

系统还会专门保留一个 `actions` 板块作为空位，不直接从 RSS 填内容，而是交给后面的 Agent 根据整份材料生成“今日行动建议”。

## 5. Agent 在整条链路里做什么

脚本阶段产出的不是最终日报，而是一份“给 Agent 用的素材包”。其中会生成：

- `raw-items.json`
  - 原始抓取后的标准化数据
- `ranked-items.json`
  - 排序后的完整候选池
- `report.json`
  - 分板块后的结构化结果
- `report.md`
  - 给 Agent 的日报写作素材

接下来 `pnpm run agent` 会调用本地提示词和项目内 vendored 的 Kami / summarizer / publisher skill，让 Agent 做两件关键事情：

- 按日报板块重新组织中文内容，而不是照搬 RSS 摘要
- 生成一份可直接阅读和打印的 HTML 日报

也就是说，前面的脚本负责“筛什么”，后面的 Agent 负责“怎么写、怎么呈现”。

## 6. 最终是怎么发布的

生成 `report.html` 之后，发布脚本会继续把日报变成几个可分发形态：

- `report.pdf`
  - 适合邮件附件和归档
- `public/reports/YYYY-MM-DD.html`
  - 归档后的网页日报
- `public/assets/report-YYYY-MM-DD.pdf`
  - 公开下载的 PDF
- `src/reports.generated.json`
  - 网站首页和归档页读取的摘要数据

之后 Vite 会把这些内容构建成静态站点，输出到 `site/`。如果配置了邮件参数，系统还会自动发送带摘要和 PDF 附件的日报邮件。

所以 Whistle 的结果不是一个孤立文件，而是一整套可浏览、可下载、可归档、可推送的日报产物。

## 7. 可以怎么做定制化

Whistle 最适合做“主题型定制”，而不是只换个 UI。常见定制方式主要有三层。

第一层是信息源定制：

- 增删 RSS 源
- 调整不同来源的权重
- 给来源打标签
- 指定来源默认归属的板块

第二层是筛选逻辑定制：

- 调整 `include` / `exclude` 关键词
- 调整工作信号和噪音信号
- 修改时间衰减、重复惩罚、板块加成等排序权重
- 改每个板块的保留条数和优先级

第三层是成稿与分发定制：

- 修改 Agent prompt，让日报更偏“新闻摘要”或更偏“编辑解读”
- 调整 Kami 模板和样式，让报告更像刊物、备忘录或内部简报
- 修改邮件标题、摘要提取方式和落地页链接
- 扩展首页、归档页、订阅页展示逻辑

换句话说，Whistle 的可定制性来自“输入规则 + 筛选规则 + 输出规则”三层分离，这也是它后续能从开发资讯扩展到 AI、产品、行业、公司追踪等方向的基础。

## 8. 当前机制的价值在哪里

这个项目最有价值的地方，不是把 RSS 自动抓下来，而是把“采集、加工、成稿、分发”连成了一条可以持续运行的流水线。用户不需要每天重新做一遍搜索、筛选、去重、排版和整理，系统会先把粗加工做好，再交给 Agent 生成更接近正式出版物的日报。

因此，Whistle 更像一个个人情报处理系统，而不是一个普通信息展示页面。
